# Сервер VLESS/REALITY своими силами: что проверено на Xray 26.3.27

**Контекст:** сервер доступа коробки (решение 30, `engine/access.py`, образ `images/xray`), 2026-09-23.
Всё ниже — исполнением на официальном образе `ghcr.io/xtls/xray-core:26.3.27` (colima) и по исходникам REALITY.

## [опыт] Ключ REALITY — тот же X25519, что у WireGuard

`xray x25519` печатает три строки: `PrivateKey`, `Password (PublicKey)` и `Hash32`.
Ключи — 32 байта в base64url без выравнивания `=` (43 символа).
Открытый ключ, посчитанный `cryptography` из закрытого (`X25519PrivateKey.from_private_bytes`), совпал с тем, что печатает `xray x25519 -i <закрытый>`.
**Как применять:** ядро делает ключ сервера своим кодом, тем же, что ключ WireGuard, меняется только кодировка; бинарь Xray ядру не нужен.

## [опыт] Имена ключей конфигурации: `target` и `raw`

Сервер с `realitySettings.target` и `streamSettings.network: raw` принимается (`xray run -test`), старые `dest` и `tcp` — тоже.
На порту не 443 Xray пишет предупреждение: `REALITY: Listening on non-443 ports may get your IP blocked by the GFW`.
**Как применять:** рендерим `target` и `raw`, порт по умолчанию 443.

## [опыт] Сайт-прикрытие решает всё, и `tls ping` этого не видит

Клиент с верным ключом, id и short id к серверу с `target: www.microsoft.com:443` не подключился ни разу — ни с отпечатком `chrome`, ни с `firefox`; в журнале сервера `REALITY: processed invalid connection …: handshake did not complete successfully`.
Тот же сервер с `dl.google.com` пускает клиента всегда.
С домашней линии владельца (коробка N100, 23.09.2026) `dl.google.com` тоже годится: проверка здоровья настоящим соединением прошла через 6 с после старта.
При этом `xray tls ping` для обоих сайтов (и для `www.apple.com`, `www.cloudflare.com`) говорит одно и то же: TLS 1.3, постквантовый обмен `X25519MLKEM768`.

**По исходникам REALITY (`tls.go`, функция `Server`):** сервер набирает сайт-прикрытие первой строкой — на каждое входящее соединение и до проверки клиента (`target, err := config.DialContext(ctx, config.Type, config.Dest)`).
Причина «handshake did not complete successfully» — последняя ветка разбора, после того как клиент прошёл проверку ключа: то есть рвалось рукопожатие, одолженное у прикрытия, а не вход.

**Как применять:**
- прикрытие по умолчанию — `dl.google.com`, настраивается в `access.target`;
- здоровье сервера проверяется только настоящим соединением через REALITY (служебный пользователь, `entrypoint.sh serve-health`), а не проверкой сайта;
- обращение к прикрытию идёт на каждое соединение от процесса сервера, значит на домашней коробке оно следует маршрутизации: в режиме `full` — через аплинк, и через Tor каждое новое соединение открывается заметно дольше.

## [опыт] Отпечаток `randomized` ломает соединение

Клиент с `fingerprint: randomized` падает на стороне клиента с `tls: CurvePreferences …` и до сервера не доходит.
**Как применять:** ссылки несут `fp=chrome`.

## [опыт] Люди на ходу: API `adu` и `rmu`

`xray api adu --server=127.0.0.1:<порт API> файл.json` добавляет людей в работающий сервер, `rmu -tag=<тег> <email>` — снимает; добавленный проходит сразу, снятый сразу теряет доступ, соединения остальных не рвутся.
Две ловушки:
- в файле для `adu` нужен целый вход с `port` — без него ответ `failed to build config: … Listen on AnyIP but no Port(s) set` и `Added 0 user(s)`;
- `xray api` выходит с кодом 0 и тогда, когда никого не добавил или не снял (`rmu` отсутствующего — `User … not found`, `Removed 0 user(s)`).

**Как применять:** ядро кладёт готовый шаблон человека (`person.json` с тегом, протоколом и портом), а скрипт входа проверяет слова ответа, а не код.
Люди, добавленные через API, живут до перезапуска: полная конфигурация, которую ядро рендерит, всегда перечисляет всех.

## [опыт] Счётчики по людям и журнал

Счётчики на человека включаются `policy.levels.0.statsUserUplink`/`statsUserDownlink` и требуют `email` у клиента.
Объект `metrics` с `listen` публикует их обычным HTTP: `GET /debug/vars` → `stats.user.<email>.{uplink,downlink}` — gRPC не нужен.
`uplink` — принятое сервером от человека, `downlink` — отправленное ему.
После перезапуска сервера счётчики начинаются с нуля.
`log.access: "none"` выключает журнал соединений: иначе Xray пишет каждое соединение с адресом назначения и email.

## [опыт] Закрыть людям саму коробку

С `sniffing` и `routing.domainStrategy: IPIfNonMatch` правило `{"ip": [частные сети, петля], "outboundTag": "block"}` не пустило человека ни на `127.0.0.1`, ни на `localhost` по имени, ни в частную сеть, а служебный пользователь проверки здоровья, у которого правило `{"user": [...], "outboundTag": "direct"}` стоит выше блока, дошёл до счётчиков на петле.
Без блока человек по ссылке достал бы API ядра: оно отвечает на петле без пароля.

## [опыт] Образ: `libcap2-bin` не удалить после `setcap`

Сервер не root и слушает 443 по файловой возможности `setcap cap_net_bind_service=+ep` на бинаре.
Удаление `libcap2-bin` после `setcap` уносит и `iproute2` — он от него зависит, — а с ним `ss`, на котором стоит проверка здоровья шлюза `run`.
**Как применять:** `libcap2-bin` остаётся в образе; инструменты образа проверяются `command -v` по одному.

## [опыт] Трафик сервера на домашней коробке — по uid, ответы людям — нет

Сервер живёт в сети хоста, и его исходящие соединения — это вывод хоста, а не транзит LAN.
Роутер метит их цепочкой `route hook output` по `meta skuid` сервера и прыгает в ту же `steer`, что и `prerouting` LAN.
Ответы людям (`ct direction reply`) выходят из того же процесса и метиться не должны: иначе в режиме `full` ответ человеку ушёл бы в аплинк и соединение умерло.
