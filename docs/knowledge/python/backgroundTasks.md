# Фоновые циклы ядра: задачи, которых никто не ждёт

**Контекст:** Telegram-бот ядра (решение 31, `api/telegram.py`), 2026-09-23.

## [грабли] Исключение в фоновом цикле глушит его молча

`serve()` в `core/vibedpn/api/tunnel.py` запускает каждый фоновый цикл через `asyncio.create_task` и ждёт только серверы uvicorn; задачи собираются `gather(..., return_exceptions=True)` лишь при остановке.
Цикл, в котором вылетело неожиданное исключение, заканчивается навсегда и без строки в журнале — до перезапуска ядра.
Каждый цикл ловит только ожидаемые им ошибки: DDNS — `OSError`, сторож выхода — `OSError` пробы и `RouterError`.
Для бота это значило бы: один сбой отчёта — и тревог больше нет, а заметить некому.
**Как применять:** у бота каждый этап такта (наблюдение, отчёт, отправка, прослушивание, запись состояния) обёрнут своей защитой: сбой пишется в журнал классом и местом (`the report failed: RuntimeError at …`) и не отнимает очередь у следующих этапов; упавшая задача прослушивания называет причину и перезапускается на следующем такте.
Текст исключения в журнал не идёт: он может цитировать запрос, а в запросе к Telegram — токен.
Тест `test_a_stage_that_fails_leaves_the_others_their_turn_and_says_so` проверяет, что при отчёте, падающем каждый такт, тревога всё равно уходит.
Общий надзор за остальными циклами ядра вынесен отдельной задачей.
