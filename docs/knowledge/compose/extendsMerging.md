# `extends` складывает списки и заменяет монтирования по цели

Проверено `docker compose config` на игрушечных файлах 2026-09-15, когда делался вид аплинка `wg-<имя>` (решение 23).
Приём генерации сервисов из базового — тот же, что у страновых потребителей (решение 20), но у выходов WireGuard он упирается в два свойства `extends`, которые в документации словами не сказаны.

## Профили складываются, а не заменяются

Базовый сервис с `profiles: [wg-client]`, сгенерированный — с `profiles: [wg-uplink]`.
В результате у сгенерированного **оба** профиля, и он запускается по любому из них:

```
COMPOSE_PROFILES=wg-uplink  docker compose config --services  -> wg-proton
COMPOSE_PROFILES=wg-client  docker compose config --services  -> wg-proton
```

Практический вывод: изолировать сгенерированный сервис от профиля базового нельзя, зато **обратное направление безопасно** — базовый сервис своих профилей не наследует.
Поэтому домашняя коробка включает только `wg-uplink`: сгенерированные выходы поднимаются, а базовый `wg-client`, чьего файла `secrets/wg-client.conf` на ней нет, не поднимается и не роняет весь `up`.

## Монтирования заменяются при совпадающей цели

Базовый монтирует `./secrets/wg-client.conf` в `/etc/wireguard/wg0.conf`, сгенерированный — `./secrets/wg-proton.conf` туда же.
В собранной конфигурации остаётся **одно** монтирование — из сгенерированного:

```
volumes:
  - type: bind
    source: …/secrets/wg-proton.conf
    target: /etc/wireguard/wg0.conf
```

То есть списки томов сливаются не конкатенацией, а по ключу-цели.
Если бы они складывались, домашняя коробка падала бы на отсутствующем файле базового сервиса (`create_host_path: false`).

## Как проверять такие догадки

Дешевле всего — два игрушечных файла и `docker compose config`: ответ приходит за секунды и не требует ни образов, ни запуска.
Рассуждение о том, «как, наверное, сливается», здесь стоит дороже проверки.
