# Контейнер-шлюз аплинка: транзит, MSS и kill-switch

## [провайдер] Шлюз с туннелем меньшего MTU обязан подрезать TCP MSS

**Контекст:** Stage 4, `wg-client` как шлюз 10.77.0.10 (2026-09-13); то же — выход пиров на VPS
(Stage 3, таблица `inet vibedpn_egress`).
**Суть:** устройства LAN и серверы в интернете договариваются о MSS по своему MTU 1500 (MSS 1460),
а туннель WireGuard уже (1420 по умолчанию, у файла пира может быть меньше). Пакет крупнее MTU
туннеля шлюз должен дробить или отвечать ICMP «fragmentation needed»; где ICMP режут (частый
случай у провайдеров и облачных фильтров), большие TCP-сегменты пропадают молча — соединение
открывается, а страница или загрузка висит. Лечится на шлюзе правкой MSS в SYN и SYN+ACK:
`tcp flags syn tcp option maxseg size set rt mtu` в цепочке с хуком `forward` — `rt mtu` берёт
MTU маршрута из кэша маршрутизации (эквивалент `iptables -j TCPMSS --clamp-mss-to-pmtu`). Правило
должно видеть обе стороны рукопожатия: в контейнере-шлюзе оно стоит первым в `forward` без условия
на интерфейс, на VPS — два правила, `iifname wg0` и `oifname wg0`, потому что там цепочка
принимает весь транзит хоста, а не только наш.
**Проверка:** `tests/wg/tunnel.sh` — хост LAN без своего WireGuard с маршрутом по умолчанию через
клиента шлёт SYN на сервер; счётчик в nft-таблице сервера видит SYN от адреса клиента в туннеле
(MASQUERADE) и ни одного с MSS больше 1400 − 40 = 1360 (MTU из файла пира). Для SYN слушатель на
порту не нужен: SYN приходит и при отказе в соединении.
**Kill-switch на транзите:** цепочка `forward` шлюза принимает только `oifname wg0`; пакет LAN,
который шлюз маршрутизировал бы мимо туннеля (адрес соседа в той же сети), отбрасывается — тест
проверяет это соседом, который напрямую отвечает, а через шлюз — нет.
**Источники:** https://wiki.nftables.org/wiki-nftables/index.php/Mangling_packet_headers
(Mangling TCP options).
