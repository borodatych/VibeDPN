# Обновление коробки висит две минуты: один из адресов GitHub — чёрная дыра

Измерено 2026-09-20 на коробке владельца (Ростелеком). `vibedpn update` дважды подряд упал одинаково:

```
fatal: unable to access 'https://github.com/borodatych/VibeDPN.git/':
Failed to connect to github.com port 443 after 133777 ms: Could not connect to server
error: install.sh failed; the box keeps running the previous version
```

Одинаковые 133 секунды в обоих случаях — это не «интернет моргнул».

## Что выяснилось

GitHub с коробки **работает**: `https://github.com` отвечает 200 за 0.46 с. Молчит ровно один
адрес:

| Адрес | Порт 443 |
|---|---|
| 140.82.121.3 | открыт |
| **140.82.121.4** | **молчит** |
| 140.82.114.4 | открыт |

Порт 22 у того же мёртвого адреса тоже молчит. Резолвер (роутер провайдера, 192.168.1.1) отдаёт то
один адрес, то другой — в момент отказа он отдавал мёртвый, через час уже живой. Отсюда и
«через раз»: обновление падает ровно тогда, когда имя разрешилось в чёрную дыру.

С машины владельца в той же сети GitHub отвечал за 2 секунды — у неё был другой адрес из ответа.

## Чего это НЕ было

- не IPv6: глобальных IPv6-адресов у коробки нет вовсе, `curl -6` отвечает мгновенным отказом
- не наши правила: адрес не входит ни в один набор `inet vibedpn_router`, доменных правил про
  github нет, выходные цепочки коробки ничего не роняют
- не команда установщика: `git fetch -q origin next` вручную проходил за секунды на том же хосте

## Что сделано

`install.sh` зовёт git через `with_retries`: короткий таймаут (30 с) и три попытки. Каждая попытка
— новый процесс, то есть новое разрешение имени, и обычно вторая берёт живой адрес. Худший случай
стал 90 секунд с внятным сообщением вместо двух минут молчания и отказа.

Лечить на стороне провайдера нечего: это его чёрная дыра на одном из anycast-адресов GitHub.

## То же на ghcr.io (замер 2026-10-15)

`sudo vibedpn update` оставался на старом коммите с пометкой «образы ещё собираются», хотя все образы
лежали в `ghcr.io`. С коробки (Ростелеком) часть вызовов `docker manifest inspect` обрывалась через
~30 с: `failed to configure transport: error pinging v2 registry: Get "https://ghcr.io/v2/":
net/http: request canceled while waiting for connection (Client.Timeout exceeded while awaiting headers)`,
другие проходили за ~10 с. `curl` на разрешённый адрес 140.82.121.33 отвечал 401 за 0.4 с: живой
адрес есть, вызов просто попадал на мёртвый.

Ошибка была в `_published`: любой отказ `docker manifest inspect` считался «не опубликовано».

Что сделано: три исхода вместо двух — опубликовано, отсутствует (реестр ответил: `manifest unknown`,
у несуществующего репозитория `denied`), не ответил (ошибка транспорта или таймаут). Не ответивший
вызов повторяется (`REGISTRY_TIMEOUT_SECONDS`, `REGISTRY_ATTEMPTS`), как `_fetch` для git. Если реестр
молчит и после повторов, поиск цели останавливается на этом коммите, а обновление пишет
«реестр не ответил» (поле `unanswered` результата, строка в карточке панели), но не «образы собираются».
