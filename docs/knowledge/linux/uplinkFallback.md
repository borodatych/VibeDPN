# Цепочка запасных выходов: маршруты таблиц выходов

**Контекст:** `routing.fallback` (решение 32) — трафик замолчавшего выхода идёт через шлюз другого.
Код: `engine/router.py` (`exit_routes`, `set_exit_route`, `read_routing`), `api/uplink.py` (`UplinkWatchers`).

## Переключается маршрут таблицы, метка остаётся

Трафик LAN метится по режиму, правилам и политикам (`0x10` — vps, `0x5x` — `wg-<имя>` …), метка ведёт в таблицу выхода.
Запасной выход — это `default via <шлюз запасного>` в таблице молчащего выхода, правила `ip rule` и наборы nft не трогаются.
Отсюда два следствия:
- Всё, что несёт метку выхода, переключается само: устройства, правила, сервер доступа, бот
- Правила nft на метке (закрытие частных сетей `upstreams.vps.lan_access`) действуют и на запасном пути

## [грабли] Снятие маршрута — по списку, а не по имени шлюза

`ip route replace default via B dev vibedpn0 table T` заменяет маршрут `via A` той же таблицы одним шагом: у маршрута метрики 0 ключ — назначение и приоритет, шлюз в ключ не входит.
Удалять так же нельзя: `ip route del default via A …` не найдёт маршрут, если там уже `via B`, и забытый маршрут через запасной выход унесёт трафик после смены цепочки.
Поэтому снятие читает `ip -j route show table T` и удаляет каждый `default` через `vibedpn0` с его собственным `gateway`.
Маршрут kill-switch (`unreachable default metric 4294967295`) у моста не числится и остаётся.

## [грабли] Маршрут таблицы зависит от чужих шлюзов

Раньше сторож выхода ставил маршрут своей таблицы сам.
С цепочкой таблица `vps` зависит от шлюзов цепочки, поэтому сторож только сообщает состояние своего шлюза, а маршруты всех таблиц считает одно место под замком.
Своя таблица ставится заново на каждом раунде (маршрут, снятый в обход ядра, возвращается), чужие — только при смене выхода.
Новая цепочка из API переставляет таблицы сразу, не дожидаясь раунда.
Выход, ещё не опрошенный после старта, не участвует: ни как своя таблица, ни как запасной.

## [грабли] Когда AdGuard рвать соединения

Соединения AdGuard, открытые через один шлюз, мертвы на другом.
Ядро помнит последний путь запросов AdGuard: шлюз или «напрямую».
Закрывает при смене пути, а остановку без смены пути (kill-switch, затем тот же шлюз) пропускает — соединения дождутся.

## [грабли] ruamel дописывает новый ключ в конец секции

`routing["fallback"] = [...]` в `CommentedMap` встал после `networks: []` — между ключом и его закомментированным примером.
Новый ключ вставляется `CommentedMap.insert` сразу после `failopen`, а список пишется в одну строку (`CommentedSeq.fa.set_flow_style()`): `fallback: [wg-second, tor]`.
Пустая цепочка удаляет ключ.

**Проверено:** 17 тестов `tests/test_fallback.py`; стенд `router.sh` — остановленный шлюз VPS, умерший сервер VPS за живым шлюзом (весь входящий трафик сервера отброшен), пустая цепочка при `failopen: true`, возврат, ядро не перезапускалось.
