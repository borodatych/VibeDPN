# Роутер LAN на хосте: метки, таблицы аплинков, kill-switch

## [архитектура] Как ядро рулит LAN в контейнеры-шлюзы, не трогая default route

**Контекст:** Stage 4, `engine/router.py`, роли `home` и `client` (2026-09-13).
**Суть:** таблица `inet vibedpn_router` в prerouting метит трафик LAN (с `lan_interface`, из
`lan_subnet`, не в LAN, не в сеть шлюзов, не на адреса самой коробки — `fib daddr type != local`)
меткой аплинка; `ip rule fwmark <метка> table <id> priority <id>` уводит его в таблицу аплинка
(`vps` — 0x10/7710 → 10.77.0.10, `dpn` — 0x20/7720 → 10.77.0.20) с маршрутом
`default via <шлюз> dev vibedpn0`. Имя моста задаётся `com.docker.network.bridge.name` — опции
сети замораживаются при создании, существующую сеть нужно пересоздать (`vibedpn down`/`up`).
Приоритет `ip rule` всегда явный (man ip-rule: «Each rule should have an explicitly set unique
priority value»). Транзит LAN ↔ `vibedpn0` и LAN ↔ LAN (прямой путь коробки на одном порту)
разрешён правилами `DOCKER-USER` с меткой `vibedpn-router` — тот же механизм, что у выхода на VPS;
группы `vibedpn-*` делят верх цепочки и не выталкивают друг друга.
**Kill-switch и failopen:** мост живёт, пока есть сеть, а не контейнер, поэтому маршрут на
остановленный шлюз сам не пропадает — трафик тонул бы в ARP. Ядро раз в 5 с шлёт шлюзу ICMP echo
(raw-сокет: в образе ядра нет `ping`, у root в контейнере есть `CAP_NET_RAW`; шлюз отвечает и с
поднятым kill-switch — ответ `established`) и по его ответу ставит или снимает маршрут шлюза.
В таблице аплинка при `failopen: false` лежит `unreachable default metric 4294967295`: пока
маршрут шлюза есть, он выигрывает по метрике, без него трафик стоит. При `failopen: true` такого
маршрута нет, и поиск уходит в основную таблицу. Порядок применения — сначала этот маршрут, потом
правило, потом метки, иначе в промежутке помеченный трафик ушёл бы мимо.
**Факты исполнением (iproute2 alpine 3.24):** `ip -j rule show` →
`{"priority":7710,"src":"all","fwmark":"0x10","table":"7710"}`; `ip -j route show table 7710` →
`{"dst":"default","gateway":"10.77.0.10","dev":"vibedpn0"}` и
`{"type":"unreachable","dst":"default","metric":4294967295}`; `ip route flush|del` в таблице,
которой ещё не было, — код 2 и «FIB table does not exist», удаление отсутствующего маршрута в
существующей — «No such process»: оба текста — «уже нет», не ошибка.
**Грабли:** `/proc/sys` в контейнере `core` смонтирован только для чтения даже с `NET_ADMIN` и
сетью хоста — `send_redirects` оттуда не выключить. Коробка на одном порту иначе рассылает
ICMP redirect «идите к роутеру напрямую»; вместо sysctl — `oifname <lan> icmp type redirect drop`
в той же таблице. `rp_filter`: systemd ставит 2 (loose) — ответы через `vibedpn0` с адресом из
интернета проходят (strict отбросил бы).
**Ревью (2026-09-13), что исправлено и почему:**
- Порядок при смене режима или аплинка: новое `ip rule` → новые метки (`nft -f`) → удаление правил
  старых меток по полному селектору (`priority` + `fwmark` + `table`). Удаление первым оставляло
  помеченный старой меткой трафик без правила — он уходил в основную таблицу мимо kill-switch.
- Наблюдатель делает `ip route replace` на каждом круге, пока шлюз отвечает: маршрут, снятый извне
  (пересозданный мост удаляет маршруты вместе с устройством, ручной `flush`), возвращается сам;
  в журнал — только смена состояния и новая ошибка.
- `rp_filter` строгий (1) на `all` или `vibedpn0` молча режет ответы шлюзов (источник — интернет,
  обратный маршрут — не мост); `/proc/sys` в `core` только для чтения, поэтому это проверка
  `doctor` с командой sysctl, а не настройка ядра.
- `doctor` проверяет и маршрут kill-switch (при `failopen: false` его отсутствие — FAIL), и
  отличает «не прочитал таблицу» от «шлюз не отвечает».
- Новые соединения из `vibedpn0` в LAN запрещены правилом группы: шлюз — сторонний образ, он
  отвечает LAN, но не открывает соединений в неё. Пересылка IPv6 из LAN через коробку отброшена.
**Осознанно оставлено:** остановленный `core` оставляет правила и маршрут шлюза как есть — утечки
нет (метки и `unreachable` на месте), но при падении шлюза в это время трафик ждёт таймаута ARP, а
при `failopen: true` прямой выход не включается, пока `core` не вернётся.
**Решение владельца (2026-09-13): выбор в UI, по умолчанию закрыто.** В `full` через аплинк `vps` устройства LAN
видны VPS как сама коробка (`wg-client` маскирует их её адресом) и открывали её панель ноды и API ядра на
адресе туннеля; на стороне VPS их не отличить. Коробка не знает адрес VPS в туннеле: в peer-файле только
свой `Address /32` и `AllowedIPs 0.0.0.0/0`. Поэтому ключ `upstreams.vps.lan_access` (по умолчанию `false`)
закрывает не адрес, а все частные диапазоны для трафика с меткой `vps` в цепочке `forward` — тот же
`EGRESS_BLOCKED_RANGES`, что VPS и так не пропускает пирам дальше себя. Единственный частный адрес за
туннелем — сам VPS, так что законный трафик не теряется, и правило работает на уже установленных коробках
без нового экспорта peer-файла. Трафик самой коробки идёт через `output`, его правило не касается.
Синтаксис проверен `nft -c` на Alpine; E2E-стенд: при `false` соединение устройства с адресом fake-VPS в
туннеле уходит в таймаут, при `true` сервер отвечает отказом, смена — без перезапуска ядра.
**Грабли smoke:** `http://1.1.1.1/cdn-cgi/trace` по HTTP отвечает 301, а не 200 — проверка
связности «код 200» давала ложный FAIL при исправном пути; критерий — любой HTTP-ответ. На VM
colima нет `ping` и `nc`.
**Политики устройств (Stage 5, 2026-09-13):** восемь nft-наборов — `devices_<политика>_mac`
(`type ether_addr`) и `devices_<политика>_ip` (`type ipv4_addr`); устройство с MAC попадает только в
набор MAC (адрес по DHCP меняется и чужой), без MAC — в набор адресов; пустые наборы `nft -c` принимает.
Исполнением на VM: `ether saddr @набор` в `inet`-таблице на хуке prerouting ловит маршрутизируемый
трафик устройства с LAN-моста (счётчик растёт), `ip saddr @набор` — тоже. Порядок в prerouting —
первым совпадением (`return`): чужой интерфейс, не IPv4, не из LAN, трафик внутри LAN и к шлюзам,
адреса коробки; потом `bypass` (без метки), `block` (метка 0x30), `vps` (0x10), `dpn` (0x20) и
последней — метка режима `full`. Метку `block` не знает ни одно `ip rule`, её отбрасывает цепочка
`forward` — устройство без выхода, но с доступом к самой коробке (DNS, UI идут в input). Аплинки «в
использовании» — аплинк режима плюс аплинки политик: у каждого своё правило, таблица с маршрутом
kill-switch и наблюдатель шлюза; `doctor` проверяет их все.
**Трафик процесса хоста через аплинк по UID (Stage 11, исполнением на colima VM, 2026-09-13):**
цепочка `type route hook output priority mangle` с правилом `meta skuid 7753 meta mark set 0x77`, `ip rule fwmark 0x77 table 7799 priority 7799`
и маршрут `default via 10.99.0.2 dev labup0 table 7799` на контейнер-шлюз (Alpine, `ip_forward=1`, `masquerade` на выходе).
DoH-запрос `curl https://1.1.1.1/dns-query` от UID 7753 (`setpriv --reuid 7753`) — HTTP 200, в счётчике `forward` шлюза 23 пакета.
Тот же запрос от root — HTTP 200, счётчик 0: метка только у своего UID.
Хук `route` пересчитывает маршрут после смены метки у уже созданного сокета; адрес источника остаётся адресом хоста, шлюз его маскирует, ответ возвращается при `rp_filter` 2.
**Грабля:** в сети colima VM имя `cloudflare-dns.com` разрешается в `0.0.0.0` (блокировка DoH-доменов резолвером сети), `curl` падает за 1 мс — DoH проверять по адресу.
