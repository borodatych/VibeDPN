# Устройства LAN: neighbour-таблица, имена, хранилище

## [провайдер] Кого видит коробка и откуда берёт имена

**Контекст:** обнаружение устройств, Stage 5 (2026-09-13), `engine/devices.py`.
**Суть:** `ip -j -4 neigh show dev <lan>` отдаёт записи `{"dst", "lladdr", "state": [...]}`. Без
фильтра `nud` не показываются только `none` и `noarp` (ip-neighbour(8)). Исполнением на VM
(iproute2 6.1.0): устройство, которое обращалось к коробке, — `{"dst":"192.168.88.2",
"lladdr":"f6:5f:…","state":["DELAY"]}`; адрес, которого нет в сети, — `{"dst":"192.168.88.9",
"state":["FAILED"]}` без `lladdr`; с `nud all` видны ещё мультикаст-записи `NOARP`. Устройство
считается увиденным, если у записи есть MAC, адрес из `lan_subnet`, это не адрес самой коробки и
состояние не `FAILED`/`INCOMPLETE`/`NOARP`/`NONE`. Таблица знает только тех, кто сам обратился к
коробке — как к шлюзу или DNS; это ровно устройства, которыми управляет роутер. Активное сканирование
подсети не делается: оно шумит в чужой сети и находит тех, кто через коробку не ходит.
**Имена:** в режиме sidecar DHCP-аренды живут на роутере провайдера, у коробки их нет (файл аренд
dnsmasq появится с режимом gateway, Stage 9). Источник — PTR через резолвер хоста: `socket.gethostbyaddr`
из контейнера `core` с сетью хоста идёт в системный резолвер (на VM вернул `host.lima.internal`
для шлюза VM и «No address associated with name» для адреса без записи — это обычный отказ).
Имя из `config.yaml` важнее PTR. PTR спрашивается до транзакции и только для нового устройства или
сменившегося адреса — медленный резолвер не держит базу.
**Хранилище:** SQLite из стандартной библиотеки в `/var/lib/vibedpn/devices.db` (`data/core`),
первичный ключ — MAC, версия схемы в `PRAGMA user_version`; база новее известной — отказ старта
ядра, а не порча.
**Источники:** https://man7.org/linux/man-pages/man8/ip-neighbour.8.html ,
https://docs.python.org/3/library/socket.html#socket.gethostbyaddr ,
https://docs.python.org/3/library/sqlite3.html .
