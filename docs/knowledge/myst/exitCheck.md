# Проверка выхода `dpn`: почему «адрес коробки» — это не утечка

Разобрано 2026-09-18 на коробке владельца. Пункт Stage 8 звучал как утечка:
`doctor --network` показывал `[FAIL] exit dpn — uplink dpn leaves with the direct address`,
и подозревали таблицу nft обёртки внутри контейнера после пересоздания.

Утечки нет. Ошибался сам вопрос, который задавал доктор.

## Что именно меряет проверка

`_gateway_exit` выполняет `docker compose exec <шлюз> wget -qO- <сервис адреса>`.
Это **собственный трафик контейнера**, путь `output`, а не транзит из LAN.
Kill-switch обёртки `images/myst-consumer/entrypoint.sh` стоит на `forward`:

```
chain forward { type filter hook forward priority filter; policy drop;
  iifname "eth0" oifname != "eth0" accept }
```

Транзит без туннеля падает в `policy drop`, а собственный трафик ноды уходит через `eth0`.
Для `wg` и `tor` совпадение получается случайно: у шлюза `wg` kill-switch накрывает и свой
исходящий трафик, у `tor` исходящий заворачивается в `TransPort`. У consumer — нет, и не должно:

**нода обязана ходить напрямую.** Ей нужны discovery, блокчейн и endpoint выходной ноды.
Стенд `tests/e2e/home.sh` этого прямо требует: «no loop: the node leaves directly while the LAN
is steered into dpn» — и падает, если трафик ноды не прямой. То есть доктор называл утечкой
ровно то, что продукт проверяет как норму.

## Чем доказано, что транзит закрыт

Проба с той же сети шлюзов, маршрутом по умолчанию через шлюз — это в точности путь пакета из LAN:

```bash
docker run --rm --network vibedpn-upstreams --cap-add NET_ADMIN alpine sh -c \
  'ip route replace default via 10.77.0.20; wget -qO- -T 10 http://api.ipify.org'
```

Результат: `download timed out` — не проходит ничего.
Тот же запрос через `10.77.0.60` (tor) вернул `107.189.30.49`, то есть метод рабочий, а не слепой.
Проверять ICMP бесполезно: Tor его не носит, и `ping` через оба шлюза молчит одинаково —
первая попытка контроля именно на этом и оказалась пустой.

На хосте в умном режиме для `dpn` вообще нет ни `ip rule`, ни таблицы 7720:
`used_uplinks` даёт таблицу только тем аплинкам, в которые кто-то отправляет трафик.
То есть на коробке в момент «утечки» через `dpn` не ходил никто.

## Как теперь звучит проверка

Доктор спрашивает у ноды `GET /connection` (`engine/consumer.py: connection_status`) и различает:

- нода не `Connected`, адреса нет или он равен адресу коробки → **warn**: «нет сессии: нода
  выходит напрямую, трафик LAN задержан»
- нода `Connected`, а адрес равен адресу коробки → **fail**: вот это утечка
- адрес отличается от адреса коробки → **ok**, чем бы нода себя ни называла

Оба прежних наблюдения ложатся в первый случай: и `download timed out` (туннель есть, сессия
мертва), и адрес коробки (туннеля нет вовсе).

## Что из этого следует для похожих проверок

Проба изнутри шлюза отвечает на вопрос «куда выходит сам шлюз», а не «куда выходит LAN».
Там, где эти два вопроса расходятся, проба нуждается в контексте — состоянии сессии, как здесь,
или в честном транзите с сети шлюзов, как в пробе выше.
