# ДВА ВАРИАНТА UI НА START0: N100 И RASPBERRY PI

Решение по первому пункту Stage 6.
UI — приложение на старт-паке start0 (Point0 + Prisma + better-auth + Bun), решение владельца 2026-09-12.
Кодовая база одна, варианта два: `full` для N100 и `lite` для Raspberry Pi.

---

## 1. Что показал замер

Стенд: Docker на VM colima, aarch64, 2 CPU, 2 ГиБ, пак start0 v0.1.23 без правок, 2026-09-13.

| Что | Значение |
|---|---|
| Сборка `bun run build` в Docker на VM 2 ГиБ | падает через 988 с: *cannot allocate memory* |
| Та же сборка нативно (Bun 1.3.14, macOS) | 79 с, пик RSS 2.18 ГиБ, `dist` 87 МБ |
| Runtime-образ arm64 (`oven/bun:1`, prod-зависимости, `dist`) | 469 МБ |
| Старт сервера после миграций | 290 мс, здоров через ~5 с после `up` |
| RSS приложения в простое | 205 МиБ |
| RSS приложения после 600 запросов (`/` и `/api/health`) | 283 МиБ |
| RSS `postgres:17-alpine` | 69–78 МиБ |
| CPU в простое | меньше 1.5 % одного ядра |

**Вывод из замера:**
Сборка UI на коробке невозможна ни на Pi, ни на N100 с 2 ГиБ.
Работающий UI с базой стоит около 360 МиБ.

## 2. Что режется для Pi

**Не режется:**
- **Postgres.** Пак привязан к нему адаптером Prisma (`@prisma/adapter-pg`), очередью `pg-boss` и backplane сокетов на LISTEN/NOTIFY. Переход на SQLite — это форк схемы и адаптеров ради ~70 МиБ.
- **better-auth.** Вход в UI обязателен в обоих вариантах. Пароль — тот же, что у `/api/`.
- **Bun.** Падение с *Illegal instruction* на ARMv8.0 (Cortex-A72 у Pi 4) исправлено в Bun v1.3.9. Пак требует `bun ^1.3.14`.

**Режется в `lite` — флагом сборки `UI_VARIANT=lite`, без форка:**
- **Воркер `pg-boss`.** Им пользуются только `modules/health/worker.ts` и `modules/axiom/provision.ts`, продукту фоновые задачи на старте не нужны. Процесс воркера не стартует.
- **Живые обновления через backplane.** Экраны статуса и устройств опрашивают API по таймеру.
- **Тяжёлые экраны:** графики истории и вкладка статистики ноды. Остаются мастер, статус, переключатели и список устройств.
- **Настройки Postgres для Pi:** `shared_buffers=32MB`, `max_connections=20`. Меньший `shared_buffers` уменьшает и RSS Postgres.

**Порог приёмки `lite`:**
- RSS приложения и Postgres вместе — не больше 300 МиБ под нагрузкой панели;
- цифры снимаются на живом Pi 4 с 2 ГБ.

Порог не выдержан — минимум Pi для роли с UI поднимается до 4 ГБ, это записывается в `docs/roles.md`.

## 3. Сборка в CI

- **Коробка UI не собирает.** Образы приходят готовыми из GHCR.
- **Задача `ui-image`:** `docker buildx` на `linux/amd64,linux/arm64` с `--build-arg UI_VARIANT=full|lite`.
- **Сборка `dist` один раз на вариант, на amd64-раннере.** `dist` не зависит от архитектуры, arm64-стадия только ставит prod-зависимости. Так сборка не упирается в память QEMU.
- **Теги:** `ghcr.io/borodatych/vibedpn-ui:${VIBEDPN_TAG}-full` и `…-lite`.
- **Смоук каждого образа:** миграции проходят, `/api/health` отвечает 200, вход без пароля — отказ.
- **Смоук arm64-образа под QEMU.** Сборка Bun с исправлением ARMv8.0 сама проверяется в QEMU с базовым CPU. Отдельная приёмка на Pi 4 всё равно обязательна: эмуляция не доказывает поведение Cortex-A72.

---

## 4. Выбор варианта в `compose.yaml`

- **Переменная `VIBEDPN_UI_VARIANT`** (`full` | `lite`) в `.env`, по умолчанию `full`.
- **Образ сервиса `ui`:** `ghcr.io/borodatych/vibedpn-ui:${VIBEDPN_TAG}-${VIBEDPN_UI_VARIANT}`.
- **Postgres UI** — отдельный сервис того же профиля `ui`, данные в `data/ui-db`, пароль генерирует `init` в `secrets/`.
- **`vibedpn init`** ставит `lite`, если памяти хоста меньше 4 ГиБ.
- **`doctor`** предупреждает, когда `full` стоит на хосте с памятью меньше 4 ГиБ.

## 5. Порядок пунктов Stage 6

1. Каркас `full` из пака: экран входа, слушает только LAN, сервис `ui` и Postgres в `compose.yaml`, задача CI `ui-image`.
2. Флаг `UI_VARIANT=lite` и замер на Pi 4 — сразу за каркасом, пока экранов мало.
3. Экраны статуса, устройств и ноды — в обоих вариантах с первого коммита.
