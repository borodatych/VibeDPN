# Возможности VibeDPN

Версионно-независимый каталог того, что умеет продукт. Одна запись на возможность; расширили
возможность — переписывается её пункт, а не добавляется второй. Планы живут в
[roadmap.md](roadmap.md), здесь только то, что уже работает.

## Платформы

Хост — Debian 12/13 или Raspberry Pi OS 64-bit на amd64/arm64 (Raspberry Pi 4/5, мини-ПК на N100,
любой Debian-хост или VPS); нужен Docker Compose v2 и ядро с WireGuard. Три роли коробки —
[roles.md](roles.md).

## Возможности

### Установка одной строкой

`install.sh` ставит всё нужное на чистый Debian-хост: Docker Engine и Compose из официального
репозитория Docker, клон репозитория в `/opt/vibedpn`, CLI `vibedpn` в venv на системном Python с
зависимостями, проверенными по sha256, и симлинк в `/usr/local/bin`. Скрипт отказывается работать на
неподдерживаемой ОС или архитектуре, а повторный запуск обновляет установку. Пошагово —
[manuals/installation.md](manuals/installation.md).

### Мастер настройки `vibedpn init`

Настраивает коробку за одну команду: сам находит интерфейс с маршрутом по умолчанию, адрес и
подсеть LAN (для VPS — публичный адрес), проверяет наличие модуля WireGuard и спрашивает только
роль, пароль веб-интерфейса и, для клиента VPS, путь к peer-файлу. Пишет `config.yaml` с
пояснениями к каждому разделу, `.env` для Compose и секреты с правами 600; всё задаваемо флагами
для автоматизации, повторный запуск защищён от случайной перезаписи (`--force` с бэкапом).

### Управление коробкой: `vibedpn up | down | restart | status | logs`

Пять команд поверх Docker Compose, которым не нужно помнить ни профили, ни каталоги: `up`
поднимает сервисы роли (и убирает контейнеры профилей, выпавших после смены роли), `down`
гасит всё, что принадлежит коробке, `restart` применяет правки `config.yaml` — `.env`
пересобирается из конфига автоматически, контейнеры перечитывают его, `status` показывает роль,
режим маршрутизации, аплинки и состояние каждого контейнера с health, `logs` отдаёт журналы
(`-f`, `--tail`). Docker не установлен, демон не запущен или нет прав на сокет — одна понятная
строка вместо вывода Docker.

### Нода Mysterium из коробки

В ролях `home` и `vps` контейнер `myst-provider` поднимается с актуальными флагами ноды, своим
каталогом данных и опубликованным UDP-диапазоном; панель ноды и её API остаются на loopback
хоста, а пароль панели задаётся тем же паролем, что и у VibeDPN, ещё в `init` — публичный
`myst/mystberry` на коробке не живёт. Состояние ноды видно без её панели: ядро отдаёт сводку
`GET /provider/stats` (версия и аптайм ноды, вердикт мониторинга сети, identity с регистрацией,
балансом и заработком в MYST, запущенные сервисы, итоги сессий — число, потребители, трафик,
заработанное), а `vibedpn status` печатает её блоком `node` под списком контейнеров; нода ещё
не ответила или ядро не запущено — вместо блока одна строка с причиной, остальной статус не
страдает.

### Файрвол VPS из коробки

Роль `vps` получает nftables-таблицу с политикой «всё закрыто, кроме нужного»: ssh (порты
берутся у самого sshd — `sshd -T`, — а без него из его конфигов со всеми `Port`, `ListenAddress`
и `Include`, чтобы не запереть владельца), порт WireGuard-сервера, UDP-диапазон ноды, трафик из
туннеля, ICMP/ICMPv6 и ответы DHCPv6 (иначе VPS с адресом по DHCPv6 теряла бы IPv6 при продлении
аренды). Правила рендерятся из конфига и применяются ядром при каждом старте одной транзакцией,
повторное применение ничего не ломает; свои сервисы добавляются двумя списками в конфиге.
Выключенный в конфиге файрвол ядро при старте снимает, а не оставляет в ядре; `doctor` сверяет
порты, на которых sshd слушает на самом деле, с открытыми в файрволе и предупреждает о таблице,
оставшейся после выключения.

### Приватный туннель: домашние коробки у своей VPS

На VPS сервер WireGuard поднимается сам: ключ создаётся один раз и хранится среди секретов, конфиг
сервера собирается из `config.yaml`. Домашняя коробка подключается одной командой на VPS —
`vibedpn peer add <имя>` выдаёт ей адрес в туннеле и печатает готовый файл WireGuard вместе с
QR-кодом (или пишет файл через `--out`), а на коробке его принимает
`vibedpn init --role client --peer-config`. Новый пир применяется к работающему серверу на месте,
соединения остальных коробок не рвутся; так же на месте `vibedpn peer rm` отключает коробку.
`vibedpn peer list` показывает каждую коробку с адресом, временем последнего handshake, трафиком и
адресом, с которого она подключилась; `vibedpn peer export` выдаёт файл повторно. С любого пира
открываются панель ноды VPS и API её ядра — на адресе сервера туннеля и больше нигде: API там
только читает состояние, а управление пирами остаётся на самой VPS. Ноутбуку или телефону, которому
нужна лишь панель, выдаётся файл с `--tunnel-only` — через туннель идёт только его подсеть. Коробка
с обычным файлом выходит в интернет через VPS и видна снаружи с её адресом: ядро включает NAT
подсети туннеля при любом `firewall.enabled` и открывает для туннеля пересылку, которую Docker
закрывает на хосте, — только от пиров наружу и ответы обратно; снаружи в туннель соединение не
открыть, чужой адрес туннеля не с `wg0` отбрасывается. Без сервера туннеля в конфиге всё это
снимается.

### Вход в панель коробки

Панель коробки на её LAN-адресе открывается только после входа паролем, который спросил `vibedpn init`.
Пароль один: тот же открывает API ядра и панель ноды.
Без входа любая страница уводит на форму входа, а API ядра под `/api/core/` отвечает 401.
Регистрации, сброса пароля по почте и входа через сторонние сервисы нет: у коробки один пользователь.
Пароль проверяется по файлу `secrets/htpasswd` при каждом входе, поэтому новый пароль из `vibedpn init --force` действует сразу, без пересборки и перезапуска.
Панель открывается и по адресу коробки, и по её имени — по умолчанию `http://vibedpn.lan`, имя задаёт `ui.host_name`.
Имя отвечает у устройств, которые спрашивают DNS у коробки: ядро само добавляет его в AdGuard и при переименовании снимает прежнее, чужие перезаписи владельца остаются. Без DNS коробки `vibedpn doctor` предупреждает, что работает только адрес.
Страница, открытая с другого имени, войти не может.
Перебор пароля ограничен: пять попыток входа за пять минут, дальше отказ до конца окна. Устройство не обходит ограничение подменой заголовков вроде `X-Forwarded-For`: считается настоящий адрес соединения.
Панель слушает только LAN-адрес коробки и не стартует без пароля и своих секретов, поэтому не оказывается открытой по ошибке.
Панель бывает в двух вариантах из одной кодовой базы: `full` для N100 и мощнее и `lite` для Raspberry Pi — без фоновых задач и с маленьким Postgres. `vibedpn init` выбирает вариант по памяти коробки, `--ui-variant` задаёт его явно, `vibedpn doctor` предупреждает, если полный вариант стоит на коробке с памятью меньше 4 ГиБ.

### DNS и адблок: AdGuard Home

На ролях `home` и `client` AdGuard Home отвечает на DNS-запросы устройств на порту 53 LAN-адреса
коробки (заглушка systemd-resolved на хосте не мешает) и ходит к серверам из `dns.upstreams` по
DNS-over-HTTPS; мастер первичной настройки не появляется. Его веб-интерфейс — на LAN-адресе и порту
`dns.web_port`, вход — пользователем `admin` с паролем из `vibedpn init`. Ядро при каждом старте
сверяет в конфиге AdGuard только своё — адрес, порт, апстримы, пароль и ответы AAAA — а фильтры и
настройки, сделанные в интерфейсе AdGuard, остаются. В режиме `full` AdGuard не отдаёт AAAA-записи,
чтобы устройства не уходили по IPv6 мимо туннеля; при смене режима ядро сообщает это работающему AdGuard
сразу, своим служебным пользователем, без перезапуска.
Конфиг AdGuard новой несовместимой схемы ядро не трогает и не стартует, объясняя почему. Как
направить устройства на коробку вручную или через DHCP роутера — в README.

### Роутер LAN: режимы `off` и `full`, kill-switch

Коробка ролей `home` и `client` работает шлюзом для устройств своей LAN: устройству указывают её
адрес шлюзом. В режиме `routing.mode: off` трафик устройств уходит в интернет напрямую через
коробку; в `full` — весь через аплинк `default_upstream` (свою VPS или сеть Mysterium), а
соединения внутри LAN и к самой коробке идут мимо. Маршрут хоста по умолчанию коробка не трогает:
каждый аплинк — отдельный контейнер-шлюз, ядро только направляет в него трафик LAN. Ядро следит,
отвечает ли шлюз аплинка: пока отвечает, трафик идёт через него; перестал — при
`routing.failopen: false` трафик устройств стоит, пока аплинк не вернётся (утечки мимо туннеля нет),
при `true` уходит напрямую. К адресам контейнеров-шлюзов устройства LAN напрямую не достучатся.
Поверх режима действует политика устройства из `config.yaml` (раздел `devices`): `bypass` —
напрямую даже в `full`, `vps` или `dpn` — через этот аплинк даже в `off`, `block` — никуда за
пределы LAN, при этом сама коробка (DNS, интерфейс) устройству доступна. Устройство с MAC узнаётся
только по MAC, без MAC — по адресу. Политику задаёт `vibedpn device set <MAC или адрес> vps|dpn|bypass|block
[--name ...]`, снимает `vibedpn device unset`: ядро само правит раздел `devices` в `config.yaml`, сохраняя
комментарии, отказывается от политики, с которой коробка не запустится, и применяет изменение сразу —
без перезапуска ядра и туннеля; если роутер изменение не принял, прежний `config.yaml` возвращается. Kill-switch и проверка шлюза работают для каждого аплинка,
который нужен режиму или политикам.
Режим и аплинк переключаются на экране статуса панели или командами `vibedpn mode off|full` и
`vibedpn upstream vps|dpn`. На поднятой коробке ядро меняет одну строку `config.yaml` с сохранением
комментариев владельца, сразу применяет роутер и режим DNS, и ничего не перезапускается: ни ядро, ни
туннель, ни AdGuard. Значение, с которым коробка не запустится, отвергается без записи, а если роутер
его не принял, прежний `config.yaml` возвращается. На остановленной коробке команда только сохраняет
значение до `vibedpn up`. `vibedpn doctor` показывает, загружен ли роутер, совпадают ли правила с
режимом и отвечает ли шлюз.

### Экран статуса панели

Главная страница панели показывает одной строкой, что сейчас с выходом в интернет: LAN идёт через
аплинк, напрямую, или выхода нет, потому что шлюз аплинка молчит и kill-switch держит трафик. Ниже —
переключатели режима (`full` — с подтверждением) и аплинка, и карточка каждого включённого аплинка:
отвечает ли шлюз, взведён ли kill-switch, когда шлюз проверялся и какая была ошибка. Экран обновляется
сам каждые 5 секунд. То же в терминале: `vibedpn status` показывает шлюзы аплинков и строку, если LAN
сейчас без выхода.

### Устройства LAN: обнаружение и список

Коробка ролей `home` и `client` сама замечает устройства своей LAN — те, что ходят через неё как
через шлюз или DNS, — и помнит их между перезапусками: MAC, последний адрес, когда появилось впервые
и когда было в последний раз. Имя берётся из `config.yaml` (раздел `devices`, по MAC, иначе по
адресу), а если там его нет — из обратного DNS роутера, который обычно знает имена по своим
DHCP-арендам. `vibedpn device list` показывает таблицу устройств с именем, адресом, MAC, политикой
из конфига и временем последнего появления. Сеть коробка не сканирует.
Устройство с политикой в `config.yaml`, которое коробка ещё не видела (например, заданное по адресу
заранее), тоже есть в списке — с пометкой «never seen», чтобы его политику можно было увидеть и снять.

Страница «Devices» панели — тот же список таблицей с поиском по имени, MAC и адресу. Политика выбирается
прямо в строке: по режиму, через VPS, через Mysterium, напрямую или без интернета; политика через
выключенный аплинк недоступна, а «без интернета» просит подтверждения. Изменение применяется сразу, без
перезапуска; если ядро его отвергло, причина видна в строке. Устройству с политикой можно дать своё имя.
Список обновляется сам раз в 30 секунд.

### Диагностика: `vibedpn doctor`

Одна команда отвечает «почему не работает»: конфиг и его производные, секреты роли, модули ядра
для туннелей и файрвола, IP-forwarding, кто занял нужные порты (свой контейнер — норма, чужой
процесс — по имени), жив ли Docker и здоровы ли сервисы роли. Каждая строка — вердикт, деталь и
команда, которую надо выполнить; ничего не чинится молча. `--json` для скриптов. С `--network` —
и то, что нельзя увидеть не выходя в сеть: внешний адрес самой коробки и адрес выхода через каждый
включённый аплинк (изнутри его контейнера-шлюза); аплинк без ответа или с адресом коробки — ошибка,
значит его трафик не идёт через туннель. Там же предупреждение, что в режиме `full` DoH-запросы
AdGuard пока уходят напрямую. Без флага `doctor` в интернет не ходит; с ним спрашивает адрес у
ipify, который по своей политике ничего не записывает.
