# Возможности VibeDPN

Версионно-независимый каталог того, что умеет продукт. Одна запись на возможность; расширили
возможность — переписывается её пункт, а не добавляется второй. Планы живут в
[roadmap.md](roadmap.md), здесь только то, что уже работает.

## Платформы

Хост — Debian 12/13 или Raspberry Pi OS 64-bit на amd64/arm64 (Raspberry Pi 4/5, мини-ПК на N100,
любой Debian-хост или VPS); нужен Docker Compose v2 и ядро с WireGuard. Три роли коробки —
[roles.md](roles.md).

## Возможности

### Установка одной строкой

`install.sh` ставит всё нужное на чистый Debian-хост: Docker Engine и Compose из официального
репозитория Docker, клон репозитория в `/opt/vibedpn`, CLI `vibedpn` в venv на системном Python с
зависимостями, проверенными по sha256, и симлинк в `/usr/local/bin`. Скрипт отказывается работать на
неподдерживаемой ОС или архитектуре, а повторный запуск обновляет установку. Пошагово —
[manuals/installation.md](manuals/installation.md).

### Мастер настройки `vibedpn init`

Настраивает коробку за одну команду: сам находит интерфейс с маршрутом по умолчанию, адрес и
подсеть LAN (для VPS — публичный адрес), проверяет наличие модуля WireGuard и спрашивает только
роль, пароль веб-интерфейса и, для клиента VPS, путь к peer-файлу. Пишет `config.yaml` с
пояснениями к каждому разделу, `.env` для Compose и секреты с правами 600; всё задаваемо флагами
для автоматизации, повторный запуск защищён от случайной перезаписи (`--force` с бэкапом).

### Управление коробкой: `vibedpn up | down | restart | status | logs`

Пять команд поверх Docker Compose, которым не нужно помнить ни профили, ни каталоги: `up`
поднимает сервисы роли (и убирает контейнеры профилей, выпавших после смены роли), `down`
гасит всё, что принадлежит коробке, `restart` применяет правки `config.yaml` — `.env`
пересобирается из конфига автоматически, контейнеры перечитывают его, `status` показывает роль,
режим маршрутизации, аплинки и состояние каждого контейнера с health, `logs` отдаёт журналы
(`-f`, `--tail`). Docker не установлен, демон не запущен или нет прав на сокет — одна понятная
строка вместо вывода Docker.

### Нода Mysterium из коробки

В ролях `home` и `vps` контейнер `myst-provider` поднимается с актуальными флагами ноды, своим
каталогом данных и опубликованным UDP-диапазоном; панель ноды и её API остаются на loopback
хоста, а пароль панели задаётся тем же паролем, что и у VibeDPN, ещё в `init` — публичный
`myst/mystberry` на коробке не живёт. Состояние ноды видно без её панели: ядро отдаёт сводку
`GET /provider/stats` (версия и аптайм ноды, вердикт мониторинга сети, identity с регистрацией,
балансом и заработком в MYST, запущенные сервисы, итоги сессий — число, потребители, трафик,
заработанное), а `vibedpn status` печатает её блоком `node` под списком контейнеров; нода ещё
не ответила или ядро не запущено — вместо блока одна строка с причиной, остальной статус не
страдает.

### Файрвол VPS из коробки

Роль `vps` получает nftables-таблицу с политикой «всё закрыто, кроме нужного»: ssh (порты
берутся у самого sshd — `sshd -T`, — а без него из его конфигов со всеми `Port`, `ListenAddress`
и `Include`, чтобы не запереть владельца), порт WireGuard-сервера, UDP-диапазон ноды, трафик из
туннеля, ICMP/ICMPv6 и ответы DHCPv6 (иначе VPS с адресом по DHCPv6 теряла бы IPv6 при продлении
аренды). Правила рендерятся из конфига и применяются ядром при каждом старте одной транзакцией,
повторное применение ничего не ломает; свои сервисы добавляются двумя списками в конфиге.
Выключенный в конфиге файрвол ядро при старте снимает, а не оставляет в ядре; `doctor` сверяет
порты, на которых sshd слушает на самом деле, с открытыми в файрволе и предупреждает о таблице,
оставшейся после выключения.

### Приватный туннель: домашние коробки у своей VPS

На VPS сервер WireGuard поднимается сам: ключ создаётся один раз и хранится среди секретов, конфиг
сервера собирается из `config.yaml`. Домашняя коробка подключается одной командой на VPS —
`vibedpn peer add <имя>` выдаёт ей адрес в туннеле и печатает готовый файл WireGuard вместе с
QR-кодом (или пишет файл через `--out`), а на коробке его принимает
`vibedpn init --role client --peer-config`. Новый пир применяется к работающему серверу на месте,
соединения остальных коробок не рвутся; так же на месте `vibedpn peer rm` отключает коробку.
`vibedpn peer list` показывает каждую коробку с адресом, временем последнего handshake, трафиком и
адресом, с которого она подключилась; `vibedpn peer export` выдаёт файл повторно. С любого пира
открываются панель ноды VPS и API её ядра — на адресе сервера туннеля и больше нигде: API там
только читает состояние, а управление пирами остаётся на самой VPS. Ноутбуку или телефону, которому
нужна лишь панель, выдаётся файл с `--tunnel-only` — через туннель идёт только его подсеть. Сейчас
туннель ведёт до самой VPS; выход в интернет через неё появится вместе с NAT на VPS.

### Диагностика: `vibedpn doctor`

Одна команда отвечает «почему не работает»: конфиг и его производные, секреты роли, модули ядра
для туннелей и файрвола, IP-forwarding, кто занял нужные порты (свой контейнер — норма, чужой
процесс — по имени), жив ли Docker и здоровы ли сервисы роли. Каждая строка — вердикт, деталь и
команда, которую надо выполнить; ничего не чинится молча. `--json` для скриптов.
