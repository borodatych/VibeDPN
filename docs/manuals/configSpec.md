# Спека `config.yaml`

> **Скопируйте этот файл целиком своей LLM и попросите: «собери config.yaml VibeDPN для …»**
> (например, «для домашней коробки с нодой и выходом через Германию» или «для VPS»). Документ
> самодостаточен: модели не нужны ни исходники, ни интернет.
>
> Канонический источник схемы — `core/vibedpn/config.py`. Здесь она изложена человеческим языком,
> а каждый полный пример ниже прогоняется через модель тестом `core/tests/test_examples.py`:
> разошлись — тест красный.

## Что это за файл

- **Где лежит:** `/opt/vibedpn/config.yaml`. Пишет `vibedpn init`; править руками можно, после
  правки — `vibedpn up`: он пересоздаёт только ядро и те службы, чьи разделы изменились.
  Исключение — то, что ядро применяет на лету через свой API: `routing` (режим, выход по умолчанию,
  правила, сети, списки; кроме `failopen`), `devices`, `upstreams.vps.lan_access` и
  `upstreams.dpn.country`. Их правку руками `up` отдаёт работающему ядру: оно перечитывает файл
  и применяет её на лету, без перезапуска. Файл, который роутер не принял, `up` называет ошибкой,
  а ядро остаётся с прежними настройками.
- **Формат:** YAML 1.2 (`off`, `no`, `yes` — строки, не булевы), UTF-8. Ключи — только те, что описаны ниже: **неизвестный ключ — ошибка**,
  опечатка не пройдёт молча.
- **Секретов в нём нет.** Ключи WireGuard, keystore ноды, пароль UI живут в `secrets/`, `data/`
  и `.env` (`chmod 600`). Файл можно показывать при разборе проблемы.
- Первая строка всегда `version: 1` — версия схемы.

## Роли: что обязательно, что запрещено

Роль задаёт, какие секции нужны. Всё, что не подходит роли, — ошибка, а не «игнорируется».

| Секция | `home` (всё в одной коробке) | `vps` (нода + сервер туннеля) | `client` (дом, пара к VPS) |
|---|---|---|---|
| `network` | обязательна | **запрещена** | обязательна |
| `routing` | обязательна | **запрещена** | обязательна |
| `devices` | можно | **запрещена** | можно |
| `upstreams.vps` | **запрещено включать** | **запрещена** | обязательно `enabled: true` (peer-файл — `secrets/wg-client.conf`) |
| `upstreams.dpn` | можно | **запрещена** | можно |
| `provider` | можно (обычно включён) | обязательно `enabled: true` | **запрещено включать** |
| `wg_server` | **запрещена** | обязательна | **запрещена** |
| `dns`, `ui` | можно (по умолчанию включены) | **запрещены** | можно (по умолчанию включены) |
| `firewall` | **запрещена** | можно (по умолчанию включён) | **запрещена** |
| `api` | можно | можно | можно |
| `access` | можно (`address` обязателен при `enabled: true`) | можно (`address` по умолчанию — `wg_server.endpoint`) | можно (`address` обязателен при `enabled: true`) |
| `ddns` | можно | можно | можно |
| `telegram` | можно | можно | можно |

## Секции

### `version`

Целое, всегда `1`.

### `role`

`home` | `vps` | `client`. Смысл ролей — в [roles.md](../roles.md).

### `network` — где стоит коробка

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `mode` | `sidecar` \| `gateway` | `sidecar` | `sidecar` — коробка стоит в существующей LAN одним портом; `gateway` — «в разрыв», WAN + LAN двумя портами |
| `lan_interface` | имя интерфейса (`eth0`, `end0`, `enp1s0`; до 15 символов) | — | интерфейс в сторону домашних устройств |
| `lan_subnet` | IPv4-сеть в CIDR (`192.168.1.0/24`) | — | адрес сети, не хоста: `192.168.1.5/24` — ошибка |
| `lan_address` | IPv4 внутри `lan_subnet` | — | адрес коробки в LAN; на нём слушают `ui` и `dns`. Закрепить на роутере (DHCP-резервация или статика) |
| `wan_interface` | имя интерфейса | — | только для `mode: gateway`, обязателен там и запрещён в `sidecar`; не равен `lan_interface` |
| `dhcp.range_start`, `dhcp.range_end` | IPv4 внутри `lan_subnet` | со 100-го хоста до пятого с конца (у /24 — `.100`–`.249`) | только для `mode: gateway`: пул адресов, который раздаёт коробка; `lan_address` в него не входит, `lan_subnet` не меньше /28 |
| `dhcp.lease` | `45m`, `12h`, `2d`, `infinite` | `12h` | только для `mode: gateway`: срок аренды |
| `wifi.ssid` | строка до 32 байт UTF-8 | — | только для `mode: gateway`: имя сети точки доступа; `lan_interface` тогда — беспроводной интерфейс |
| `wifi.country` | ISO 3166-1 alpha-2 | — | страна радио: какие каналы и мощность разрешены; регистр не важен |
| `wifi.band` | `"2.4"` \| `"5"` (в кавычках) | `"2.4"` | диапазон, ГГц |
| `wifi.channel` | целое | `6` | 1–13 для 2.4, 36–165 для 5 |
| `wifi.security` | `wpa2-wpa3` \| `wpa3` | `wpa2-wpa3` | `wpa2-wpa3` пускает и старые устройства без WPA3; `wpa3` — только WPA3-SAE |

В `gateway` коробка — роутер своей LAN: раздаёт адреса (шлюз и DNS — `lan_address`), выпускает прямой трафик LAN через `wan_interface` с NAT.
Адрес `lan_address` на `lan_interface` настраивает система, не VibeDPN; `vibedpn doctor` проверяет, что он стоит.

```yaml
network:
  mode: gateway
  lan_interface: wlan0
  lan_subnet: 192.168.50.0/24
  lan_address: 192.168.50.1
  wan_interface: enp1s0
  dhcp:
    range_start: 192.168.50.100
    range_end: 192.168.50.249
    lease: 12h
  wifi:
    ssid: "Home"
    country: DE
    band: "2.4"
    channel: 6
    security: wpa2-wpa3
```

Пароля сети в `config.yaml` нет: он лежит в `secrets/wifi-passphrase`, его создаёт `vibedpn init`, показывает `sudo vibedpn wifi show`, а заменяет на свой `sudo vibedpn wifi passphrase` (8–63 символа ASCII, точка доступа перезапускается).
Точку доступа поднимает сервис `hostapd` (профиль Compose `wifi`); адрес на беспроводном интерфейсе, как и в любом gateway, назначает система.

### `routing` — политика LAN-трафика

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `mode` | `off` \| `full` \| `smart` | `off` | `off` — всё напрямую; `full` — всё через `default_upstream`, кроме устройств с политикой; `smart` — по правилам `domains`, остальное напрямую, устройства с политикой — как в `full` |
| `default_upstream` | `vps` \| `dpn` \| `tor` \| `wg-<имя>` | — (обязателен) | куда идёт трафик в `full`/`smart`. Если `mode` не `off`, аплинк должен быть включён в `upstreams`. У `home` — `dpn`, `tor` или свой выход `wg-<имя>` из `upstreams.wg` |
| `failopen` | bool | `false` | `false` — упал аплинк, трафик устройств с политикой `vps`/`dpn` стоит (kill-switch); `true` — уходит напрямую, осознанный выбор |
| `domains` | список правил | `[]` | правила `mode: smart`, по одному на сайт; старый ключ `smart_domains` (список суффиксов) читается как правила через `default_upstream` |
| `domains[].domain` | домен | — | покрывает и поддомены (`kinopoisk.ru` — и `www.kinopoisk.ru`); приводится к нижнему регистру |
| `domains[].via` | `vps` \| `dpn` \| `wg` \| `tor` \| `direct` | — | канал сайта; аплинк `vps`/`dpn`/`tor` должен быть включён в `upstreams`, `wg` — свой выход из `upstreams.wg` |
| `domains[].country` | ISO 3166-1 alpha-2 | нет — любая | только для `via: dpn`: страна выхода; разные страны у разных сайтов работают одновременно |
| `domains[].uplink` | имя из `upstreams.wg` | — (обязателен для `wg`) | только для `via: wg`: какой свой выход; выход должен быть включён. Разные сайты могут идти через разные выходы одновременно |
| `domains[].learn` | bool | `true` | CDN, которые устройство запрашивает сразу после сайта, идут его каналом сами; выученное хранит ядро, его видно и можно снять в панели и `vibedpn` |
| `domains[].also` | список доменов | `[]` | CDN, закреплённые за сайтом вручную («вести как родителя») |

Один домен не может встречаться дважды — ни как `domain`, ни в `also`.

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `lists` | список | `[]` | готовые списки сайтов и сетей по URL для `mode: smart`; каждый домен и каждая сеть списка идут каналом списка |
| `lists[].url` | `http://` или `https://` URL | — | текстовый файл: по домену в строке, строки hosts-файла (`0.0.0.0 example.org`), `\|\|example.org^` или сеть IPv4 `a.b.c.d/nn` (так публикует сети antifilter); `#` и `!` — комментарии; один URL дважды — ошибка |
| `lists[].via` | `vps` \| `dpn` \| `wg` \| `tor` \| `direct` | — | канал всех доменов и сетей списка; аплинк должен быть включён в `upstreams` |
| `lists[].country` | ISO 3166-1 alpha-2 | нет — любая | только для `via: dpn`: страна выхода, как у правила |
| `lists[].uplink` | имя из `upstreams.wg` | — (обязателен для `wg`) | только для `via: wg`: свой выход, как у правила |

Ядро скачивает список при старте и раз в сутки, хранит копию в `data/core/lists/` и при недоступном URL работает по копии.
Правило `domains` для того же имени сильнее списка; CDN за доменами списка не выучиваются.
Сети списков проверяются после `networks` и до доменов: своя сеть владельца сильнее списка, сеть списка сильнее домена. Строка с одним адресом без `/nn` сетью не считается.
Пример списка сетей: `https://community.antifilter.download/list/community.lst` (около 900 сетей); у `antifilter.download` этот путь отвечает 404.

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `networks` | список | `[]` | сети адресов для `mode: smart` — для приложений, которые ходят по адресу, а не по имени (Telegram) |
| `networks[].network` | IPv4-сеть `a.b.c.d/nn` | — | адрес сети, не хоста: `149.154.167.51/20` — ошибка; IPv6 не принимается; одна сеть дважды — ошибка |
| `networks[].via` | `vps` \| `dpn` \| `wg` \| `tor` \| `direct` | — | канал всех адресов сети; аплинк должен быть включён |
| `networks[].country` | ISO 3166-1 alpha-2 | нет — любая | только для `via: dpn` |
| `networks[].uplink` | имя из `upstreams.wg` | — (обязателен для `wg`) | только для `via: wg` |

Сеть сравнивается с адресом назначения, ничего не резолвится и не выучивается.
Сеть `direct` сильнее сети через выход, сети проверяются раньше правил доменов.
Проще командами: `vibedpn net add <сеть> <канал>`, `vibedpn net rm <сеть>`, `vibedpn net list` — применяется сразу.
Официальный список сетей Telegram: https://core.telegram.org/resources/cidr.txt (берутся строки IPv4).

### `devices` — устройства с собственной политикой

Список; каждый элемент:

| Ключ | Тип | Смысл |
|---|---|---|
| `name` | строка 1–64 | как показывать в UI |
| `mac` | `aa:bb:cc:dd:ee:ff` (регистр и `-` не важны) | основной идентификатор |
| `ip` | IPv4 | запасной идентификатор; нужен хотя бы один из `mac`/`ip` |
| `policy` | `vps` \| `dpn` \| `tor` \| `bypass` \| `block` | поверх `routing.mode`: `bypass` — напрямую даже в `full`; `vps`/`dpn`/`tor` — через этот аплинк даже в `off`, аплинк должен быть включён; `block` — никуда за пределы LAN, сама коробка (DNS, UI) доступна |

Один и тот же `mac` или `ip` дважды — ошибка. Устройство с `mac` узнаётся только по MAC — `ip` у него
не учитывается (адрес по DHCP меняется); устройство без `mac` — по `ip`.

Раздел можно править руками (после правки — `vibedpn up`: ядро перечитает файл и применит его на лету), но проще командами
`vibedpn device set <mac|ip> vps|dpn|bypass|block [--name ...]` и `vibedpn device unset <mac|ip>`: ядро
само меняет одну запись, сохраняет комментарии, отказывается от политики, с которой коробка не
запустится, и применяет изменение без перезапуска. Запись, которой не было, получает имя из
`--name`, иначе имя устройства из обратного DNS роутера, иначе `device-<хвост MAC или адреса>`.

### `upstreams` — аплинки

```yaml
upstreams:
  vps:
    enabled: true                    # peer-файл лежит в secrets/wg-client.conf, в конфиге его нет
    lan_access: false                # устройства LAN к панели ноды и API VPS через туннель; по умолчанию закрыто
  dpn:
    enabled: true
    country: DE                      # ISO 3166-1 alpha-2; нет строки — любая страна
```

- `vps` — приватный WireGuard-туннель к своей VPS (контейнер `wg-client`). Только роль `client`.
  Peer-файл от `vibedpn peer export` на VPS `init --peer-config` кладёт в `secrets/wg-client.conf`;
  путь фиксированный, поэтому в конфиге не упоминается.
  `lan_access` (bool, по умолчанию `false`) — пускать ли устройства LAN, чей трафик идёт через этот
  туннель (режим `full` или политика `vps`), к частным адресам за ним: там только панель ноды и API ядра
  VPS. Закрыто — роутер отбрасывает такой трафик к 10/8, 172.16/12, 192.168/16, 100.64/10 и 169.254/16;
  сама коробка VPS видит всегда. Меняется на экране статуса панели без перезапуска.
- `dpn` — consumer Mysterium: выход через ноду сети. `country` — двухбуквенный код, регистр не
  важен; кавычки не нужны (`NO` — Норвегия, файл читается как YAML 1.2, где это строка).
- `wg` — собственные выходы по готовому файлу WireGuard, по одному на имя (решение 23):

```yaml
upstreams:
  wg:
    proton:                          # имя: буквы в нижнем регистре, цифры и «-», до 24 знаков
      enabled: true                  # по умолчанию true; false — оставить настройку, но не поднимать
    mullvad: {}                      # пустая запись — тоже включённый выход
```

  Файл выхода кладётся в `secrets/wg-<имя>.conf` — путь фиксированный, поэтому в конфиге его нет.
  Коробка не знает, чей это файл: бесплатный тариф Proton, платный поставщик или вторая своя коробка.
  Файл нужен обязательно: без него сервис выхода не поднимется, и коробка его не создаёт сама.
  Каждое имя получает свой контейнер-шлюз `wg-<имя>`, адрес `10.77.0.50+i` и таблицу маршрутизации;
  порядок — по алфавиту имён, не более восьми выходов.
  Ключ такого выхода в маршрутизации — `wg-<имя>`; он годится для `routing.default_upstream`.
  Отдельный сайт или список уходит через такой выход правилом `via: wg` с `uplink: <имя>`.
- `tor` — бесплатный выход через сеть Tor по мостам (решение 27): без аккаунта, оплаты и регистрации.

```yaml
upstreams:
  tor:
    enabled: true                    # по умолчанию false
    # bridges: не писать — по умолчанию встроенные мосты Snowflake из Tor Browser
    bridges:                         # свои мосты, если встроенные не проходят
      - "obfs4 203.0.113.9:443 0123456789ABCDEF0123456789ABCDEF01234567 cert=... iat-mode=0"
```

  Контейнер-шлюз `tor`, адрес `10.77.0.60`, ключ маршрутизации `tor` — годится для `default_upstream`,
  для `via: tor` у правил, списков и сетей и для политики устройства `tor`.
  Только TCP: сайты и Telegram работают, UDP (звонки, игры, QUIC) отбрасывается, браузеры сами уходят на TCP.
  Скорость через Snowflake — около 1 Мбит/с. После запуска шлюзу нужна минута-две на подключение к Tor;
  пока он не подключился, трафик выхода стоит, а не уходит напрямую.
  `bridges` — строки мостов в том виде, в каком их пишет Tor после слова `Bridge`: транспорт, адрес, остальное.
  Транспорт — `snowflake`, `obfs4` или `meek_lite` (для них в образе есть клиенты); `webtunnel` не поддерживается.
  Ключа `bridges` нет — используются встроенные мосты Snowflake Tor Browser (в `config.yaml` они не выписываются).
  Включается `vibedpn tor enable`, выключается `vibedpn tor disable`, смотрится `vibedpn tor show`;
  в панели — карточка на странице «Выходы». Пошагово — [torUplink.md](torUplink.md).

- `xray` — выход через маскирующий транспорт по ссылке владельца (решение 29): там, где рукопожатие
  WireGuard не проходит, соединение выглядит обычным TLS к обычному сайту.

```yaml
upstreams:
  xray:
    enabled: true                    # по умолчанию false
```

  Больше в `config.yaml` ничего нет: ссылка `vless://…` несёт учётные данные сервера и лежит в
  `secrets/xray-link` (права 600). Кладёт её туда `vibedpn xray enable` — аргументом ссылка не
  принимается, потому что аргументы видны в `ps` и остаются в истории оболочки.
  Контейнер-шлюз `xray`, адрес `10.77.0.70`, ключ маршрутизации `xray` — годится для
  `default_upstream`, для `via: xray` у правил, списков и сетей и для политики устройства `xray`.
  Только TCP, как у Tor; DNS идёт прежним путём. Из транспортов ссылки принимаются `tcp`, `ws` и
  `grpc`, из защиты — `none`, `tls` и `reality`; ссылки `ss://` не принимаются. Всё непринятое
  отвергается с объяснением, а не игнорируется молча.
  Сервер недоступен — трафик отбрасывается, мимо туннеля не уходит.
  Выключается `vibedpn xray disable`, смотрится `vibedpn xray show` (адрес сервера и вид
  транспорта, без учётных данных). Пошагово — [xrayUplink.md](xrayUplink.md).

### `ui` на роли `vps` — панель внутри туннеля

На ролях `home` и `client` панель включена по умолчанию и слушает адрес коробки в LAN.
На роли `vps` она **выключена по умолчанию**: это публичная машина, и умолчание, открывающее
веб-интерфейс на арендованном сервере, — то самое, которое никто не читает, пока не поздно.

```yaml
ui:
  enabled: true                    # на роли vps по умолчанию false
```

Включённая панель VPS слушает **только адрес туннеля** (`10.78.0.1`, первый адрес
`wg_server.subnet`) — на публичном адресе её нет. Порт открывается в файрволе тем же способом, что
и панель ноды: правилом для интерфейса `wg0`, то есть попасть в неё может только домашняя коробка,
уже находящаяся в туннеле.

### `provider` — нода Mysterium

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | bool | `false` | раздавать канал и получать MYST |
| `udp_ports` | `"start-end"` | `"56000-56100"` | UDP-диапазон ноды (флаг `--udp.ports`); пробрасывать на роутере |
| `traversal` | список из `manual`, `upnp`, `holepunching` | `[manual, upnp, holepunching]` | порядок обхода NAT (флаг `--traversal`): проброс руками, UPnP, hole punching. Минимум один, без повторов |

Диапазон — строка в кавычках, 1–65535, `start <= end`.

### `wg_server` — сервер приватного туннеля (только `vps`)

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `endpoint` | hostname или IPv4 | — (обязателен) | что домашние коробки набирают: публичный адрес VPS |
| `subnet` | IPv4-сеть | `10.78.0.0/24` | адреса туннеля; сервер берёт первый, минимум `/30`. Смена при существующих пирах: при старте `core` переносит их в новую подсеть с теми же ключами и пишет в лог, кого куда, — каждой перенесённой коробке нужно выгрузить файл заново (`vibedpn peer export`); подсеть, куда пиры не помещаются, — ошибка старта |
| `listen_port` | 1–65535 | `51820` | UDP-порт сервера |

Ключ сервера и `wg0.conf` в конфиг не пишутся: `core` генерирует ключ один раз в
`secrets/wg-server/server.key` и рендерит `secrets/wg-server/wg0.conf` из этой секции при каждом старте.

### `dns` — AdGuard Home

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | bool | `true` | DNS и адблок на порту 53 LAN-интерфейса |
| `upstreams` | список URL `https://…` | `[https://dns.cloudflare.com/dns-query]` | апстримы DNS-over-HTTPS; минимум один |
| `web_port` | 1–65535 | `3000` | веб-панель AdGuard на LAN-интерфейсе |

### `ui` — веб-интерфейс коробки

| Ключ | Тип | По умолчанию |
|---|---|---|
| `enabled` | bool | `true` |
| `port` | 1–65535 | `80` |
| `host_name` | доменное имя (`[a-z0-9-]`, хотя бы одна точка, регистр и крайние точки отбрасываются) | `vibedpn.lan` |
| `variant` | `full` \| `lite` | `init` выбирает по памяти хоста: `lite` меньше 4 ГиБ, иначе `full`; флаг `--ui-variant` — явно |
| `language` | двухбуквенный код ISO 639-1 (`ru`, `en`, …; регистр не важен) | `ru` |

Слушает только LAN-интерфейс, пускает после входа паролем из `init` и отдаёт API ядра под `/api/core/`.
`host_name` — имя, по которому устройства открывают панель: при `dns.enabled` ядро держит в AdGuard перезапись этого имени на `network.lan_address` (одну свою; перезаписи владельца не трогает, при переименовании прежняя снимается). Вход разрешён со страницы, открытой по адресу или по этому имени. Без `dns` имя нужно завести в DNS роутера самому.
`language` — язык панели, пока браузер не выбрал другой переключателем в шапке: английский встроен в панель, остальные языки — файлы `data/ui/locales/<код>.json` коробки (формат — `docs/manuals/languageFileSpec.md`); языка без файла нет, и панель говорит по-английски.
На том же языке пишет Telegram-бот (`telegram`): его строки — ключи `bot.*` того же файла, поэтому смена `language` при `vibedpn up` пересоздаёт и ядро.
`variant` выбирает образ панели: `full` — для N100 и мощнее, `lite` — для Raspberry Pi (без фоновых задач и backplane сокетов, Postgres с `shared_buffers=32MB` и `max_connections=20`). Сменили — `vibedpn up`.

### `firewall` — файрвол VPS (только `vps`)

nftables-таблица `inet vibedpn`, на вход всё закрыто, кроме: ssh, порта `wg_server`, UDP-диапазона
ноды, с туннеля `wg0` — только панели ноды (4449) и API ядра (`api.port`), ICMP и перечисленного ниже;
пакеты к подсети туннеля, пришедшие не через `wg0`, отбрасываются. `core` применяет её при каждом старте.

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | bool | `true` | выключить — `core` при старте снимает таблицу, VPS остаётся с тем, что настроил хостер (`vibedpn down` таблицу не снимает) |
| `ssh_ports` | список портов | `[22]` | `init` берёт порты у самого демона (`sshd -T`: `port` и `listenaddress host:port`), без него — из `sshd_config` и `Include` (все `Port`, `ListenAddress` с портом, разделители как у sshd: пробел, таб или `=`); пустой список — ошибка, чтобы не запереть себя; `doctor` сверяет список с реальными портами sshd |
| `allow_tcp` | список портов | `[]` | другие TCP-сервисы владельца на этой же VPS |
| `allow_udp` | список портов | `[]` | другие UDP-сервисы владельца |

### `access` — сервер доступа по ссылке

Свой маскирующий сервер VLESS/REALITY для своих людей: каждому ссылка `vless://` и QR-код
(`vibedpn access add <имя>` или страница «Доступ» панели). На коробке с LAN человек снаружи выходит
так же, как устройство дома: по режиму `routing.mode`, правилам сайтов и сетей, через AdGuard; на VPS —
прямо в интернет. Сама коробка и сети вокруг неё (петля, RFC 1918, CGNAT, link-local) для людей закрыты.
Пошагово, с пробросом порта и DDNS, — [accessServer.md](accessServer.md).

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | bool | `false` | включить сервер; профиль Compose `access`, контейнер `access` |
| `address` | hostname или IPv4 | на `vps` — `wg_server.endpoint`, на `home` и `client` обязателен | что называют ссылки: имя, которое следует за коробкой (`ddns`), или публичный адрес |
| `port` | 1–65535 | `443` | TCP-порт сервера на всех адресах хоста; на другом порту REALITY заметнее, Xray сам об этом предупреждает |
| `target` | доменное имя | `dl.google.com` | сайт, чьё рукопожатие TLS 1.3 одалживает REALITY; годится не любой сайт — проверка здоровья контейнера пробует его настоящим соединением |

Ключ сервера и список людей в конфиг не пишутся: `core` делает ключ один раз в
`secrets/access/server.json` и ведёт людей в `secrets/access/people.json`. Смена `port` или `target`
пересоздаёт при `vibedpn up` ядро и сервер; смена `address` — только ядро: сервер и соединения людей
не трогаются, новые ссылки называют новый адрес, а выданные раньше по-прежнему называют старый.

### `ddns` — имя, которое следует за адресом коробки

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | bool | `false` | ядро раз в пять минут узнаёт внешний адрес и при его смене — и раз в сутки — вызывает адрес обновления сервиса DDNS |

Адрес обновления несёт токен и в конфиг не пишется: он лежит в `secrets/ddns-url` (задаётся
`vibedpn ddns set`, принимается только `https://`). Если сервис хочет адрес в самой ссылке, на его
место ставится `{ip}`. Как прошёл последний вызов — `vibedpn ddns show`.

### `telegram` — Telegram-бот коробки

Тревоги и недельный отчёт в чат владельца; бот живёт в ядре, на любой роли.
В Telegram он ходит так же, как устройство дома без своей политики: по режиму, правилам сетей и правилу домена `telegram.org`, и kill switch выхода держит и его.
Пошагово — [telegramBot.md](telegramBot.md).

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | bool | `false` | бот пишет, когда есть токен и привязанный чат; включает `vibedpn telegram set` |
| `alert_after_seconds` | 15–86400 | `60` | выход или точка Wi-Fi, молчащие дольше, — повод для тревоги; сбой короче в тревогу не попадает |
| `timezone` | зона базы tz: `Europe/Moscow`, `Asia/Yekaterinburg`, … | `Europe/Moscow` | часы сообщений и отчёта; часы самой коробки могут стоять в другом поясе |
| `report.enabled` | bool | `true` | недельный отчёт |
| `report.weekday` | `monday` … `sunday` | `monday` | день отчёта |
| `report.hour` | 0–23 | `10` | час отчёта по `timezone` |

Токен бота и чат в конфиг не пишутся: они лежат в `secrets/telegram.json` (задаёт `vibedpn telegram set`).
Из панели и CLI раздел меняется на лету, без перезапуска; правка файла руками доходит до ядра при `vibedpn up` — раздел входит в отпечаток ядра.
Язык сообщений — `ui.language`.

### `api` — API ядра

| Ключ | Тип | По умолчанию |
|---|---|---|
| `port` | 1–65535 | `4480` |

Ядро слушает `127.0.0.1`; на LAN его отдаёт `ui`. На VPS ядро на том же порту слушает ещё и адрес
сервера туннеля (первый хост `wg_server.subnet`): туда пускают только адреса туннеля и только на
чтение `/health` и `/provider/stats` — управление пирами остаётся на loopback. На порту 4449 того же
адреса проброшена панель ноды.

## Полные примеры

Каждый блок — законченный валидный конфиг (первая строка `# example: …` — метка для теста).

### `home` — всё в одной коробке

```yaml
# example: home
version: 1
role: home
network:
  mode: sidecar
  lan_interface: eth0
  lan_subnet: 192.168.1.0/24
  lan_address: 192.168.1.50
routing:
  mode: full
  default_upstream: dpn
  failopen: false
  domains: []
devices:
  - name: TV
    mac: aa:bb:cc:dd:ee:01
    policy: bypass
  - name: Work laptop
    ip: 192.168.1.42
    policy: block
upstreams:
  dpn:
    enabled: true
    country: DE
provider:
  enabled: true
  udp_ports: "56000-56100"
  traversal: [manual, upnp, holepunching]
dns:
  enabled: true
  upstreams:
    - https://dns.cloudflare.com/dns-query
  web_port: 3000
ui:
  enabled: true
  port: 80
api:
  port: 4480
telegram:
  enabled: true
  alert_after_seconds: 60
  timezone: Europe/Moscow
  report:
    enabled: true
    weekday: monday
    hour: 10
```

### `vps` — нода и сервер туннеля, без LAN

```yaml
# example: vps
version: 1
role: vps
provider:
  enabled: true
  udp_ports: "56000-56100"
  traversal: [manual, upnp, holepunching]
wg_server:
  endpoint: 203.0.113.7
  subnet: 10.78.0.0/24
  listen_port: 51820
firewall:
  enabled: true
  ssh_ports: [22]
  allow_tcp: []
  allow_udp: []
access:
  enabled: true
  port: 443
  target: dl.google.com
api:
  port: 4480
```

### `client` — дома, в паре с VPS

```yaml
# example: client
version: 1
role: client
network:
  mode: sidecar
  lan_interface: end0
  lan_subnet: 192.168.0.0/24
  lan_address: 192.168.0.2
routing:
  mode: full
  default_upstream: vps
  failopen: false
upstreams:
  vps:
    enabled: true
  dpn:
    enabled: false
dns:
  enabled: true
ui:
  enabled: true
```

## Как из конфига получается `.env`

`vibedpn init` пишет `.env` для `compose.yaml`; всё в нём, кроме `VIBEDPN_TAG`, — производные
от этого файла (`Config.env_vars()`), руками их не править: `COMPOSE_PROFILES`, `VIBEDPN_API_PORT`,
`VIBEDPN_LAN_IP` и `VIBEDPN_UI_PORT` (роли с LAN), `VIBEDPN_MYST_UDP_FROM/TO` и
`VIBEDPN_MYST_TRAVERSAL` (если включён provider).

| Роль | Профили |
|---|---|
| `home` | `provider` (если `provider.enabled`), `consumer` (если `upstreams.dpn.enabled`), `router`, `dns` (если `dns.enabled`), `ui` (если `ui.enabled`) |
| `vps` | `provider`, `wg-server` |
| `client` | `consumer` (если `upstreams.dpn.enabled`), `wg-client`, `router`, `dns`, `ui` (по включённости) |

Порядок в строке всегда канонический: `provider, consumer, wg-server, wg-client, router, dns, ui`.
