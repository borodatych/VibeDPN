# Торрент-клиент на коробке

Необязательная служба: Transmission на коробке с LAN (роли `home` и `client`; на `vps` её нет).
Закачками управляет панель, браузер до самого Transmission не доходит: его веб-интерфейс наружу не открыт,
RPC слушает `127.0.0.1`, а панель говорит с ним через ядро (`/api/core/torrents/*`).
Загрузки лежат вне каталога коробки и в резервную копию не попадают.

## Включить

```
sudo vibedpn torrents enable
sudo vibedpn up
```

Или сразу при настройке: `sudo vibedpn init --torrents`.
`enable` делает пароль RPC в `secrets/transmission-rpc-pass` (600, один раз: существующий не заменяется),
`up` создаёт папки загрузок, пишет `data/transmission/config/settings.json` и запускает контейнер `transmission`.
Образ `lscr.io/linuxserver/transmission` закреплён тегом (`TRANSMISSION_TAG` в `compose.yaml`), контейнер идёт на сети хоста
под своим пользователем `7756` — по нему роутер узнаёт его трафик.

Выключить: `sudo vibedpn torrents disable`, затем `sudo vibedpn up`. Контейнер исчезает, скачанное и состояние клиента остаются.
Что сейчас: `vibedpn torrents show`.

## Куда выходит трафик

По умолчанию `direct` — напрямую, мимо туннелей, как выходит с коробки любой ее собственный трафик.
Свой канал задаётся независимо от `routing.mode` для LAN:

```
sudo vibedpn torrents egress vps      # direct, vps, dpn, tor, xray или wg-<имя>
sudo vibedpn up
```

Канал должен быть включённым выходом коробки, иначе конфиг не пройдёт проверку.
Роутер метит трафик пользователя `7756` в цепочке `torrents_output` и отправляет его в особую таблицу выхода.
Она держит трафик, когда выход молчит: клиент не уйдёт ни на адрес провайдера, ни на запасной выход, как бы ни стояли `failopen` и `fallback`.
IPv6 клиента мимо выхода не уходит. DNS клиент спрашивает у того же резолвера, что и коробка, и имена трекеров по этому пути могут пойти мимо выхода.
Через `tor` ходит только TCP: DHT и uTP не работают, а скорость мала — `vibedpn doctor` предупреждает об этом.

Живой проверки с настоящим выходом нет: правила `torrents_output` разбирает настоящий `nft`, а выбор канала проверяют тесты роутера (см. «Что не проверено»).

## Входящие соединения и порт

Peer-порт (`torrents.peer_port`, 51413) клиент слушает на всех адресах хоста.
UPnP и NAT-PMP выключены (`port-forwarding-enabled: false`), коробка не открывает порт на роутере провайдера сама.
Без проброса торренты качаются и раздают по уже установленным соединениям, но скорость и число пиров ниже.
Нужен вход снаружи — пробросьте этот порт на адрес коробки на домашнем роутере сами.
Если выход клиента не `direct`, входящие снаружи до него не дойдут в любом случае: ответы на уже пришедшее идут обычным путём, а свои соединения клиент открывает через выход.

## Диск для загрузок

По умолчанию — папка `/srv/vibedpn/downloads` на системном диске. Лучше внешний диск: ext4, exfat или ntfs.

```
vibedpn torrents storage list            # UUID, метка, файловая система, размер, почему нельзя
sudo vibedpn torrents storage use 1234-ABCD
sudo vibedpn up
```

`use` записывает `torrents.storage` (`uuid` и `fstype`) и `download_dir: /srv/vibedpn/usb/downloads`.
`up` ставит юнит systemd `srv-vibedpn-usb.mount` (диск по UUID в `/srv/vibedpn/usb`, `nofail`) и drop-in Docker, который ждёт диск.
Системный диск, неподдерживаемые файловые системы (vfat и другие) и устройства без UUID не предлагаются.
Вернуться на системный диск: `sudo vibedpn torrents storage clear`, `sudo vibedpn up`; на диске ничего не удаляется.
Из панели то же идёт через `GET` и `PUT /torrents/storage` ядра: ядро просит хост посмотреть диски, записывает выбор в `config.yaml` и просит применить его.

Что на диске нужно знать:
- exfat и ntfs не хранят владельцев, поэтому параметры монтирования отдают все файлы пользователю клиента (`uid=7756`); ext4 хранит владельцев сам, и `up` отдаёт ему папки.
- ntfs монтирует ядерный драйвер `ntfs3`; том, который Windows оставила «грязным», сначала чинится на Windows (`chkdsk`) или `ntfsfix` из пакета `ntfs-3g`.
- Нет диска при `vibedpn up`: клиент не запускается, остальная коробка работает, `up` говорит об этом, а `vibedpn doctor` показывает ошибку «torrents disk». Подключили диск — `sudo vibedpn up`.
- Отключили диск, пока клиент работает: у клиента остаётся устаревшее монтирование, он пишет ошибки. После возврата диска — `sudo vibedpn restart`.
- Клиент никогда не пишет в пустую точку монтирования на системном диске: источник bind-монтирования обязан существовать (`create_host_path: false`).

## Скорость и место

`torrents.speed_limit_down` и `torrents.speed_limit_up` — кБ/с, `null` — без ограничения. Из панели их ставят на лету, ядро ещё и записывает их в `config.yaml`;
рукой в `config.yaml` — `sudo vibedpn up` передаст их работающему клиенту без перезапуска.
`torrents.min_free_gib` — меньше свободного места в папке загрузок `vibedpn doctor` считает ошибкой.

## Проверка

`sudo vibedpn doctor` для включённого клиента проверяет:
- `torrents disk` — диск из `torrents.storage` смонтирован;
- `torrents rpc` — RPC отвечает на пароль из `secrets/`;
- `torrents folder` — пользователь клиента может писать в `<download_dir>/complete`;
- `torrents space` — места не меньше `min_free_gib`;
- `torrents egress` — для выхода не `direct` в роутере есть цепочка `torrents_output`.

А контейнер `transmission` попадает в обычную проверку служб.

## Копия коробки

`vibedpn backup` берёт `data/` целиком, а загрузки лежат вне его: `vibedpn up` отказывается работать, если `download_dir` внутри каталога коробки.
На случай, если папка всё же оказалась внутри (конфиг правили позже), копия исключает её явно; в копию идёт только состояние клиента (`data/transmission/config`, мегабайты).
Пароль RPC в копии есть (`secrets/`), как и остальные секреты.

## Что не проверено

- Настоящий USB-диск и перезагрузка коробки с подключённым и отключённым диском: юнит проверен на петлевых образах ext4, exfat и ntfs в виртуальной машине (`docs/knowledge/transmission/storage.md`).
- Выход клиента через настоящий выход (`vps`, `dpn`, `xray`, `wg-<имя>`): правила разобраны настоящим `nft` и покрыты тестами, но стенда с реальным туннелем для клиента нет.
- Tor как выход клиента.
- Ядра Debian 12 и 13: наличие `exfat` и `ntfs3` в них не проверено.
