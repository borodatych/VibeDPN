# Project Structure

`@/*` maps to `src/*` and should stay the only source alias. For files outside
`src`, use their real project-root paths in docs and scripts, for example
`public/site.webmanifest`.

## Root Directories

`src` contains the application code.

`public` contains static files served as-is, such as favicons, manifests,
images, and fonts.

`docs` contains project documentation and architecture notes.

## Source Directories

`@/modules` is for the technical and supporting machinery of the app —
infrastructure and capabilities the project relies on but that are not
themselves the product. Examples: auth, prisma, email, form, env, worker, i18n,
payments, analytics, error tracking, seed. A module need not be generic — but
when something is reusable across projects almost unchanged (a payment provider,
a logger, an email sender), that portability is a strong sign it's a module.

`@/features` is for the product itself — behavior that is unique to this project
and defines how it feels and delivers value to the user. Examples: the admin
panel (`admin`), user management (`user`), the subscription/support product
(`subscription`), search, and the open-source project pages (`opensource`). A
feature may compose modules, own its routes/pages, expose API handlers, run
workers, include scripts, and keep feature-specific docs or tests.

The split is about _what kind of thing_ it is — the product vs. the supporting
machinery — not about dependency direction. A payment provider like
`dodopayments` or `tribute` is a module — generic plumbing, reusable in another
project almost unchanged; `github` is a feature — it shapes what a subscriber
actually gets (repo access), even though all three plug into the `subscription`
feature the same way. Modules and features may freely reference each other: a
module like `auth` or `payments` can read from a product feature, and a feature
composes modules. That overlap is expected and fine. Do not add events,
indirection, or extra layers purely to keep a module "pure" — keep the code
direct and readable.

`@/lib` is for compact project-level building blocks that are important enough
to name, but not large enough to become a module yet. If one of these files
grows into multiple files or starts to own a domain, move it into `@/modules`.

`@/utils` is for tiny generic helpers. Keep helpers focused and import them from
the file where they are defined.

`@/utils/index.ts` is only for very small shared utilities such as `cn`. Do not
turn it into a barrel file for all utilities. Shadcn-related code expects this
file to exist.

`@/components/ui` contains low-level base UI primitives, usually generated by or
compatible with shadcn.

`@/components/blocks` contains larger ready-to-use UI blocks built from
primitives and project patterns.

`@/components/other` contains shared components that do not fit `ui` or
`blocks`, for example app helpers, wrappers, and integration components.

`@/components/hooks` contains shared React hooks.

`@/layouts` contains only general layouts. Feature-specific or module-specific
layouts should live inside the feature or module that owns them.

`@/pages` contains pages that do not belong to a specific feature or module,
such as home, start, privacy policy, and terms pages.

`@/api`, if you add it, is for project-level API endpoints not tied to any
domain. Prefer a feature or module `api.ts` whenever the endpoint belongs to one
— that's the usual case, so `@/api` often won't exist.

`@/assets` contains bundled assets imported from code, such as SVGs, images, and
icons.

`@/styles` contains global styles and shared CSS utilities.

`@/types/index.ts` contains reusable type utilities.

`@/types/global.d.ts` contains global type declarations.

`@/generated` contains files generated by tools such as Point0. Treat generated
files as build output unless a generator explicitly requires them to be
committed.

`@/test` contains shared test setup, preload scripts, helpers, and top-level
smoke tests.

`@/scripts` contains project-level command-line scripts.

## Entrypoints

Root-level source files in `src` describe the runtime shell of the app:

- `app.client.tsx` and `app.server.ts` are the client and server app
  entrypoints.
- `engine.ts` configures the app engine (both sides).
- `index.client.tsx` and `index.client.html` bootstrap the browser client.
- `preload.ts` contains server preload setup.

Keep domain logic out of these files. They should wire modules, features, and
framework runtime pieces together.

## Module/Feature Structure

The exact shape depends on the module or feature, but these names should stay
consistent when they apply:

`client.ts` or `client.tsx` contains client-side logic. It may still be imported
during SSR, so keep browser-only behavior explicit.

`server.ts` contains server-only logic.

`api.ts` contains Point0 queries, mutations, and actions.

`shared.ts` contains code intentionally shared between client, server, and API
layers.

`worker.ts` contains background worker logic.

`webhook.ts` contains webhook handlers.

If this file becomes too large, replace the file with a directory using the same
name and split the logic inside it.

`pages`, `layouts`, `components`, `hooks`, `server`, `client`, `test`,
`scripts`, `templates`, `fields`, and `utils` directories are also widely used
in modules and features, so they are listed here too. Add another directory when
your code needs it.

If a module or feature needs something for admins, add an `admin` directory
inside it and put all admin-related code there (as the `user` feature does with
`user/admin/*`).

## Naming Rules

Keep file and directory names in kebab-case.
